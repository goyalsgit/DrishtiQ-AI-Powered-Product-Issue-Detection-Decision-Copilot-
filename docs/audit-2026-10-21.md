# DrishtiQ code, dashboard and reference-project audit

Audit date: 2026-10-21. This is a source review and targeted verification, not proof
that every defect has been found or a security certification.

## Verdict in simple language

The components fit the current task: SQLite keeps original reviews, MiniLM/Chroma
finds review evidence, LangChain exposes Python tools, LangGraph bounds tool use,
and Gemini drafts an explanation. More frameworks are not the main need.

The application is an **evidence-assisted review investigation prototype**. It is
not a complete company feedback platform, a verified root-cause detector, or a
production-ready multi-user service.

## Findings and disposition

| Priority | Finding | Impact | Action |
|---|---|---|---|
| High | Final answers were free Markdown with no enforced report schema | UI could display malformed reports or invented citations | Implemented typed narrative and source checks in `src/reporting.py` |
| High | Search returns matches for all four no-evidence benchmark questions | Irrelevant evidence can influence answers | Remains open; add independently labelled relevance and held-out abstention evaluation |
| High | A matching quote does not establish claim support | “One bottle leaked” can be misrepresented as “every bottle is defective” | Explicitly marked unverified; semantic grounding evaluation required |
| High | No persistent AI-report storage/approval | Reports are lost on session/server restart; no review/resume audit trail | Add storage and LangGraph checkpoint/interrupt/resume after report reliability |
| Medium | Benchmark requested 3 results, tool requests 6 | Earlier numbers did not characterize the tool's retrieval limit | Ran and saved a separate top-6 diagnostic; model query rewriting is still unevaluated |
| Medium | Final writer saw original text plus tokenizer-decoded passages | Decoded text could be quoted as if verbatim | Final writer now receives only canonical original review text |
| Medium | Small-sample warning was easy to miss outside comparisons | Single-review months can look like strong trends | Added visible sample-size notice above tabs |
| Medium | SQL results panel omitted average rating | Report evidence view was incomplete | Added average rating to the SQL table |
| Medium | Old session reports could survive an output-format change | New UI could show a pre-validation report | Added report-format version to session invalidation |
| Medium | Single product and month(s) are the only agent scope | Cannot answer “best product across the database” or arbitrary date ranges | Documented; add dedicated SQL-backed tools only when these questions enter scope |

## Changes made during this audit

The dashboard's evidence-collection graph now finishes with a short completion
message. A separate native JSON call then generates `InvestigationContent`.
The extra report call is bounded to one attempt; it adds latency and token cost.
Existing four-model-turn/six-tool-call limits still bound evidence collection.
The learning CLI retains its original Markdown lesson behavior.

The final content includes:

- evidence status: supported, insufficient evidence or metrics only;
- findings separated into reported problems and positive feedback;
- citations containing review ID, month and a short original quote;
- optional possible causes, each with a verification step and source references;
- limitations and next investigation steps.

Validation rejects missing/extra/wrong-type fields, unsupported status combinations,
empty required citations, unknown IDs, wrong periods and quotes not contained in
original source text. The result attaches scope and statistics from application/SQL
data, rather than asking the model to recreate the numerical fields.

The UI renders these fields as text. If validation fails, it shows a safe error
category, retains original tool evidence and withholds the generated narrative.
The downloaded report does not include the rejected raw model output.

This does **not** check semantic entailment, prove that an issue is representative,
or detect every invented number inside free-text statements. A regression test
deliberately demonstrates that boundary. The app still calls the output a draft.

## Verification performed

- 56 offline tests passed with zero failures, errors or skips. Scripted models
  test application behavior and rejection paths, not Gemini answer quality.
- `pip check`: no broken installed requirements.
- Real local MiniLM/Chroma integration check passed: chunking, repeated indexing,
  dataset/product/month isolation, review deduplication and original-source lookup.
- SQLite read-only integrity check returned `ok`; no foreign-key violations.
- Database inspected: 932 reviews, 8 products; historical dates 2012-12-24 to
  2023-02-25. Largest product-month has 11 reviews.
- Opened the dashboard in Chrome; verified scope, SQL metrics, form, progress,
  six retrieved sources and failure display.
- A live appearance-problem question reached Gemini, SQL and semantic search.
  Its final report was rejected for a quote mismatch. The source-only final
  context change followed that finding. A subsequent dashboard run produced a
  schema/source-checked `insufficient_evidence` response. That is not a successful
  supported-answer quality check; inspect its evidence coverage and false-refusal
  behavior before claiming live reliability. A later attempt to inspect the full
  response was interrupted by a native screen-capture error. The offline pass is
  not a substitute for this unfinished supported-answer check.

All runs use the existing 24 development questions: 20 answerable, four without
evidence. Assistant-reviewed labels still need independent review. Precision uses
requested k as denominator; queries often have only one relevant review. These
are direct retrieval queries, not generated search queries, final-answer accuracy
or held-out performance. Zero scope violations and duplicate results were measured.

## Real repository comparison

These are public examples inspected as references, not independently verified
production deployments. Remote source was read, not installed or executed.

| Reference | What the inspected implementation does | Useful difference for DrishtiQ |
|---|---|---|
| [LangChain retrieval-agent-template, graph.py](https://github.com/langchain-ai/retrieval-agent-template/blob/main/src/retrieval_graph/graph.py) | Separate query generation, retrieval and response nodes; Pydantic search-query output for follow-up turns | Clean stage boundaries and configurable components. Our task also needs exact SQL and source checks. The example's final response is not itself a validated business report. |
| [ReviewLensAI, chat-rag/index.ts](https://github.com/aidenmak0624/ReviewLensAI/blob/main/supabase/functions/chat-rag/index.ts) | Resolves product namespace server-side, checks user/product access, retrieves review chunks, streams answers and citation metadata | Learn from authorization, scope isolation and citation display. Its prompt assumes retrieved matches are relevant; we should not copy that assumption. |
| [ReviewLensAI, promptfoo configuration](https://github.com/aidenmak0624/ReviewLensAI/blob/main/LLMtests/promptfoo/promptfooconfig.yaml) | Six cases check citation syntax, refusal wording and report structure using string/JavaScript assertions | Useful repeatable application checks, but citation syntax alone does not establish factual support. This inspected config is not evidence of a comprehensive LLM-judge benchmark. |
| [Streamlit 30DaysOfAI, day23.py](https://github.com/streamlit/30DaysOfAI/blob/main/app/day23.py) | Customer-review RAG instrumented through TruLens/Snowflake; evaluates answer relevance, context relevance and groundedness | Evaluate retrieval and generation separately. We can adopt that evaluation design without migrating this local app to Snowflake. |

Inference from these comparisons: the valuable additions are stronger source
handling, evaluation and persistence—not the largest possible dependency list.
None of these references establishes a target accuracy score for our dataset.

## Which additional library or MCP capability helps?

| Addition | Decision | Concrete use / acceptance gate |
|---|---|---|
| Pydantic + existing Gemini structured-output API | Used now; no new package needed | Enforce final report fields and source checks |
| Sentence Transformers cross-encoder reranker | Experiment next, not installed blindly | Compare relevance on human-reviewed development data, then held-out questions; measure latency and abstention tradeoffs |
| A hybrid lexical/vector retriever | Experiment only with a measured baseline | Check exact defect terms/IDs that semantic-only retrieval misses |
| LangGraph SQLite/PostgreSQL checkpointer | Add with persistent approval stage | Restart and resume the same investigation; enforce approval status |
| SQLAlchemy + a PostgreSQL/MySQL driver | Add when the actual database target/schema is known | Read-only adapter, migration/integration tests and index synchronization |
| One evaluation/tracing tool: e.g. TruLens or LangSmith | Optional after the evaluation contract is defined | Track runs, datasets, grounding scores, latency and tokens; review tracing data exposure |
| MCP server/client | Defer until a real external consumer/source exists | Expose our scoped `get_review_metrics`, `search_review_evidence`, `compare_review_periods` to another AI client, or consume an authorized external data service |

MCP standardizes tool access; it does not add knowledge or improve retrieval by
itself. The current Streamlit process can directly call its local Python tools.
The [LangChain MCP adapter repository](https://github.com/langchain-ai/langchain-mcp-adapters)
illustrates adapting MCP tools to LangChain. Check the installed-version API before
integration; don't mix sample code from different releases.

The [Gemini integration reference](https://reference.langchain.com/python/langchain-google-genai/chat_models/ChatGoogleGenerativeAI/with_structured_output)
documents the native JSON-schema path used here. Its presence does not remove the
need for application validation or provider-specific live checks.

## Next acceptance checks

1. **Live final-report reliability:** run a metrics-only question, one appearance
   complaint, a two-period question and an unanswerable question. Verify schema
   acceptance, literal quotes, displayed SQL numbers, incomplete/error status and
   total usage. Record rejected outputs by safe category and false rejection rate.
2. **Grounding:** independently inspect every generated claim against its source.
   Test invented defect claims, overgeneralization, numerical prose and instructions
   embedded inside review text. Do not count format checks as grounding accuracy.
3. **Retrieval quality:** review labels, create unseen positive/negative questions,
   compare filtering/reranking/hybrid retrieval, freeze settings, then evaluate.
4. **Persistent workflow:** save report plus source/version metadata, implement
   approval/resume, test restart, duplicate submissions and rejected report handling.
5. **Operational data and scope:** agree the database schema and desired questions.
   Add range/product comparisons with explicit SQL tools. For issue-specific rates,
   label all eligible reviews consistently; retrieved top-k examples cannot provide
   the denominator. Validate issue labels before plotting complaint trends.
6. **Deployment:** authentication, per-user authorization, dependency review/lock,
   context and cost budgets, backups, data retention and load tests.

Beginner explanation: **SQL gives numbers, RAG finds examples, Gemini interprets,
validation checks the report contract, and a person still verifies the meaning.**
